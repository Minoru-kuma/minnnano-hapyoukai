# 現行発表会 UI 設計

このアプリは履歴一覧から発表会を選ぶ管理ソフトではない。画面全体は、端末内の「現在の発表会」が 0 件か 1 件かで切り替わる。個人情報を画面経路へ入れず、対象指定には ID を使う。

## 最上位の状態

| 状態 | 画面 | 主操作 |
| --- | --- | --- |
| 現行発表会なし | 「発表会を登録しましょう」 | 「新しい発表会を始める」 |
| 現行発表会あり | 現行発表会のホーム | 発表会情報、部、今年の参加者、出演者名簿、演奏・曲、プログラム確認、年度終了 |

`RecitalApp` はこの二状態を表示する最小の Compose ルートである。初期読み込み、読み込み失敗時の再試行、発表会名を入力して開始する操作を提供する。発表会一覧、過去発表会の編集・削除、履歴ブラウズは作らない。

ホームの各導線を広げる前に、Room の参加者制約と単一発表会制約を利用する。未実装の大規模編集画面を仮の操作として見せず、以後は次の順で追加する。

1. 発表会情報と部
2. 出演者名簿と今年の参加者選択
3. 演奏・曲（参加者だけを候補にする）
4. プログラム確認
5. PDF 保存、任意のアーカイブ、年度終了

## 入力と編集

- 名簿の登録は、名前、区分、生徒の現在学年、任意の登録済み担当講師を扱う。名簿登録だけでは今年の参加にしない。
- 「今年の参加者」で名簿から選択する。演奏編集の候補もこの人だけに限定する。参加解除は、演奏に使われている場合に理由を表示して拒否する。
- 一つの演奏には生徒・講師を任意人数で並べ、同じ人を二度追加しない。出演者の削除は演奏から外すだけで、名簿を削除しない。
- 一つの演奏には複数曲を並べられ、曲なしの入力途中状態は「曲が未登録」と表示する。
- 作曲家の同一性と表示文字列を区別する。候補に関連付けても現在入力した表示文字列は維持し、「この表記を使う」を明示選択した場合だけ置換する。空白・略称・全半角・句読点を自動変換しない。
- 部、演奏、出演者、曲は「上へ」「下へ」で並べる。端のボタンは無効にし、読み上げラベルには対象名を含める。

保存中は進行状態を示して二重保存を防ぐ。保存失敗時は入力を残し、日本語の一般的なメッセージだけを表示する。戻る際に未保存の変更があれば破棄確認を表示する。SQL、スタックトレース、他人の個人情報をエラー文に含めない。

## プログラム確認と年度終了

プログラム確認は発表会名、日付、会場、部、各部で 1 からの演奏番号、全出演者、学年、曲名、曲ごとの作曲家表示を縦に表示する。講師連弾・生徒と講師の共演・複数曲・未登録曲を省略しない。

PDF は年度終了前の主出力であり、最終確認画面から保存する。必要なら同じ確定値からバージョン付きの機械可読アーカイブも保存する。保存成功を確認してから「年度終了」を有効にし、確認画面で削除対象（部、参加者、演奏、出演者関係、曲）と残る対象（名簿、学年、担当講師、作曲家）を明示する。出力試行だけで作業データを削除しない。

## スマートフォン利用

主要な本文は 16sp 前後、タップ領域は 48dp 以上を目安にする。縦スクロールと文字の折り返しを前提にし、通常のスマートフォンで横スクロールを必要としない。アイコンのみの操作には説明ラベルを付け、色だけで区分・選択・エラーを表さない。キーボード、システムバー、文字拡大時にも保存操作が隠れない余白を確保する。

Compose の画面状態は ViewModel、永続データは Repository 経由の Room から取得する。回転とプロセス再生成時の編集下書き復元は、各編集画面を実装する時点で `SavedStateHandle` を含めて検証する。ネットワーク、リモート分析、外部ログは使用しない。
