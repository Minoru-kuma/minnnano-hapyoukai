## 本番移行の修正

最大 Recital ID を保持し、他の発表会に属する `Piece` → `PerformanceMember` → `Performance` → `Section` → `Recital` をこの順に明示的に削除する。各子テーブルの削除条件は元の部・演奏の所属をたどり、親を先に消さない。現行発表会の作業データと、再利用する `Performer`・`Composer`・`ComposerAlias` は保持する。参加者は削除後に残った演奏メンバーだけから重複なく作る。

外部キー CASCADE に依存せず、移行トランザクション内で `PRAGMA foreign_keys` を変更しない。テスト専用の factory や PRAGMA 設定による回避も追加していない。スキーマ形状は同じため、DB version 2 とエクスポート済みスキーマを維持した。

## 移行テスト

`AppDatabaseMigrationTest` の既存テストを強化し、0 件と 1 件のケースを追加した。

| v1 の発表会数 | 確認内容 |
| --- | --- |
| 0 件 | マスターを保持し、発表会・作業データ・参加者は空 |
| 1 件 | 発表会と全配下の値・順序・曲なし演奏を保持し、実際の演奏メンバーだけを参加者に移す |
| 3 件 | 最大 ID の発表会だけを保持し、他の発表会と全配下を削除。挿入順・日付・子 ID の大小に影響されない |

全ケースで標準の `MigrationTestHelper` の外部キーが無効であることを読み取りで確認し、その状態でも移行が成功することを検証した。移行前に保持対象とマスターの全行を記録し、移行後の全行と比較するため、件数だけでなく ID・名前・日付・会場・学年・表示順・正確な作曲家表記も保持されることを確認する。

複数人・複数曲・曲なし演奏、複数演奏に出演する同じ人の参加者が一行だけになること、旧発表会にだけ出演する人と未使用のマスターが参加者に混入しないことも確認した。全ケースで `PRAGMA foreign_key_check` は違反なし。

## 既存の検証

- Repository と DB の両方で、現行発表会を一件に制限すること。
- 当年参加者だけを演奏へ追加でき、使用中の参加者は解除できないこと。
- 担当講師が登録済み講師への一貫した参照であること。
- 年度終了で発表会固有データだけが消え、出演者・作曲家は残ること。
- 複数出演者・複数曲・表示順・曲ごとの作曲家表記を保持すること。
- 複合保存の失敗時のロールバックと、全子要素を要求する並べ替えを確認すること。
- 通常更新での親 ID 変更と担当講師の自己参照を拒否し、失敗後のデータを保持すること、通常編集を保存できること。

前回調整した Debug 実行時の serialization core 1.8.1 は維持し、Room 移行テストの `AbstractMethodError` も再発していない。

## 適用範囲と検証境界

今回の修正は今後の v1 → v2 移行に適用される。既に旧移行処理で v2 になったデータベースに残る孤立行を修復する処理は追加していない。

親 ID の不変性と担当講師の種別・自己参照の検証は Repository 境界で実施する。DAO の直接操作ではこれらの検証を回避できる。また、既存の `activeSlot` 一意索引は同じ slot の重複を防ぐが、異なる slot の Recital を直接挿入する操作まで禁止するものではない。通常の Repository は slot を固定し、現行発表会を 0 件または 1 件に制限する。
