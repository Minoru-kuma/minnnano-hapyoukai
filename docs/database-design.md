# Room 基盤の設計

このデータベースは端末内で「現在準備している一つの発表会」を扱う。過去の発表会を閲覧する履歴データベースではない。UI は DAO を直接操作せず、`RecitalRepository` のトランザクション API を利用する。

## 保存範囲

| 区分 | エンティティ | 年度終了後 |
| --- | --- | --- |
| 再利用する名簿 | `Performer`、`Composer`、`ComposerAlias` | 残す |
| 現在の発表会 | `Recital`、`Section`、`RecitalParticipant`、`Performance`、`PerformanceMember`、`Piece` | 削除する |

`Performer` は `STUDENT` / `TEACHER` を持つ。生徒の現在学年と担当講師は名簿の現在値であり、学年履歴は保存しない。担当講師は同じ名簿内の `TEACHER` への外部キーで、Repository も「生徒だけが設定可能」「参照先は講師」を検証する。

`RecitalParticipant` は今年参加する人を表す複合キーの関係である。名簿にいることは参加を意味しない。演奏に加えられるのは、この関係で選択済みの人だけであり、演奏に使用中の参加者は解除できない。

## 一つの現行発表会

`recitals.activeSlot` の一意索引を使い、新規の `Recital` は常に `activeSlot = 1` で作る。これにより Repository の事前検査だけでなく、同時書き込みや DAO の誤用でも二つ目の現行発表会を保存できない。全ての発表会固有の読み取りは `activeSlot = 1` を結合条件にする。

v1 は複数行を許していたため、v1 → v2 移行では削除を避け、最大 ID の旧レコードだけを現行として選ぶ。残りは `activeSlot = NULL` の移行互換レコードとなり、v2 の通常 API・UI からは参照できない。新規作成経路はこの状態を作らない。旧データに「どれが現在か」を記録していなかったため、この選択は復元不能な情報を捏造せず、データを失わないための明示的な互換方針である。

## 演奏、順序、作曲家表記

`PerformanceMember` は演奏と名簿を結び、複合主キーにより同じ人の重複を防ぐ。複数の生徒・講師を同じ演奏に登録できる。`Piece` は演奏ごとに複数持て、未登録の曲がある演奏も途中状態として残せる。

部・演奏・出演者・曲はそれぞれ `displayOrder` を持つ。並べ替え API は同じ親の子 ID 全件を重複なしで受け取らなければ失敗する。新規演奏は生徒を含めば既存の講師のみ演奏の前、講師のみなら末尾に置くが、保存後の手動順は変更しない。

`Piece.composerId` は作曲家同一性への任意参照、`composerDisplayText` はその曲に表示する不変の入力値である。作曲家・別表記の編集や削除は、既存曲の表示文字列を書き換えない。

## 年度終了と最終出力

PDF と任意の機械可読アーカイブは、年度終了の前に確定する。`finalizedProgramSnapshot()` は発表会名・日付・会場・表示順・出演者名・その時点の学年・曲名・作曲家表示文字列を値としてコピーするため、後年の名簿編集は出力済みの PDF／アーカイブを変えない。

出力成功の確認後だけ `endCurrentRecital()` を呼ぶ。この操作は `Recital` を削除し、外部キー CASCADE により部、参加者、演奏、出演者関係、曲を一括削除する。名簿と作曲家は削除しない。出力と削除を一つの自動操作にはしない。

## 移行と検証

Room は version 2、スキーマは `app/schemas/` に出力する。`MIGRATION_1_2` は担当講師列・現行発表会索引・当年参加者表を追加し、既存の演奏参加者を選ばれた現行発表会の参加者として移す。`AppDatabaseMigrationTest` が v1 スキーマからの移行と外部キーを検証する。

アプリデータは端末内に置き、クラウドバックアップ・端末移行から除外する。ネットワーク権限、外部 API、遠隔分析、実在の個人情報を含むフィクスチャは導入しない。
