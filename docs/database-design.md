# Room 基盤の設計

このデータベースは端末内で「現在準備している一つの発表会」を扱う。過去の発表会を閲覧する履歴データベースではない。UI は DAO を直接操作せず、`RecitalRepository` のトランザクション API を利用する。

## 保存範囲

| 区分 | エンティティ | 年度終了後 |
| --- | --- | --- |
| 再利用する名簿 | `Performer`、`Composer`、`ComposerAlias` | 残す |
| 現在の発表会 | `Recital`、`Section`、`RecitalParticipant`、`Performance`、`PerformanceMember`、`Piece` | 削除する |

`Performer` は `STUDENT` / `TEACHER` を持つ。生徒の現在学年と担当講師は名簿の現在値であり、学年履歴は保存しない。担当講師は同じ名簿内の `TEACHER` への外部キーで、Repository も「生徒だけが設定可能」「参照先は別の登録済み講師」を検証する。更新対象の ID と担当講師 ID の一致を明示的に拒否し、講師から生徒への変更時も自己参照を認めない。生徒の担当になっている講師は、生徒に変更したり削除したりできない。

`RecitalParticipant` は今年参加する人を表す複合キーの関係である。名簿にいることは参加を意味しない。演奏に加えられるのは、この関係で選択済みの人だけであり、演奏に使用中の参加者は解除できない。

## 一つの現行発表会

`recitals.activeSlot` の一意索引を使い、新規の `Recital` は常に `activeSlot = 1` で作る。これにより Repository の事前検査だけでなく、同時書き込みや DAO の誤用でも二つ目の現行発表会を保存できない。全ての発表会固有の読み取りは `activeSlot = 1` を結合条件にする。

v1 は複数行を許していたため、v1 → v2 移行では最大 ID の旧レコードだけを現行として残す。旧発表会の曲 → 出演者関係 → 演奏 → 部 → 発表会の順に明示的に削除し、移行中の外部キー CASCADE に依存しない。`Performer`、`Composer`、`ComposerAlias` は独立したマスターデータなので残る。移行後に非現行の発表会レコードを保持しないため、アクティブDBには常に発表会が 0 件または 1 件だけ存在する。

## 演奏、順序、作曲家表記

`PerformanceMember` は演奏と名簿を結び、複合主キーにより同じ人の重複を防ぐ。複数の生徒・講師を同じ演奏に登録できる。`Piece` は演奏ごとに複数持て、未登録の曲がある演奏も途中状態として残せる。

部・演奏・出演者・曲はそれぞれ `displayOrder` を持つ。並べ替え API は同じ親の子 ID 全件を重複なしで受け取らなければ失敗する。新規演奏は生徒を含めば既存の講師のみ演奏の前、講師のみなら末尾に置くが、保存後の手動順は変更しない。

通常の更新 API は、保存済みデータと更新値の親 ID を同じトランザクション内で比較する。`Section.recitalId`、`Performance.sectionId`、`Piece.performanceId`、`ComposerAlias.composerId` の変更は拒否し、元データを保持する。現行発表会の所属確認にも保存済みデータを使う。名前・表示順・曲名・別表記名の通常編集は可能であり、曲の `composerId` は編集可能な参照として扱う。

`Piece.composerId` は作曲家同一性への任意参照、`composerDisplayText` はその曲に表示する不変の入力値である。作曲家・別表記の編集や削除は、既存曲の表示文字列を書き換えない。

## 年度終了と最終出力

PDF と任意の機械可読アーカイブは、年度終了の前に確定する。`finalizedProgramSnapshot()` は発表会名・日付・会場・表示順・出演者名・その時点の学年・曲名・作曲家表示文字列を値としてコピーするため、後年の名簿編集は出力済みの PDF／アーカイブを変えない。

出力成功の確認後だけ `endCurrentRecital()` を呼ぶ。この操作は `Recital` を削除し、外部キー CASCADE により部、参加者、演奏、出演者関係、曲を一括削除する。名簿と作曲家は削除しない。出力と削除を一つの自動操作にはしない。

## 移行と検証

Room は version 2、スキーマは `app/schemas/` に出力する。`MIGRATION_1_2` は担当講師列・現行発表会索引・当年参加者表を追加する。選ばれなかった旧発表会の作業データと発表会本体を子から親の順に削除した後、残った現行発表会の既存演奏参加者だけを当年参加者として移す。同じ人が複数の演奏に出る場合も参加者は一人一行である。発表会が 0 件なら参加者も空、1 件ならその発表会と全ての作業データを保持する。

移行は Room が管理するトランザクション内で実行する。外部キーが無効でも削除できる SQL を使い、移行内で `PRAGMA foreign_keys` を変更しない。今回の修正は移行処理だけを変更し、v2 のスキーマ形状は変えない。`AppDatabaseMigrationTest` が発表会 0 件・1 件・複数件の移行、保持対象の値と順序、マスターデータ保持、参加者の移行、`PRAGMA foreign_key_check` に違反がないことを検証する。実機結果は [検証結果](build-verification.md) を参照する。

この修正は v1 → v2 の移行時に適用する。既に旧移行処理で v2 になったデータベースに残る孤立行の修復は対象に含めない。

アプリデータは端末内に置き、クラウドバックアップ・端末移行から除外する。ネットワーク権限、外部 API、遠隔分析、実在の個人情報を含むフィクスチャは導入しない。
